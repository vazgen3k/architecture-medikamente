# Аудит мер по обеспечению безопасности данных As-Is

## Краткое описание текущего состояния

В текущей архитектуре большая часть данных хранится локально в офисе компании:

- Excel-файлы с журналами приёма пациентов;
- Excel-файл со списком пациентов;
- папки пациентов на файловом сервере;
- сканы, PDF и JPG с медицинскими картами, анкетами, договорами и результатами анализов;
- файловая база «1С:Бухгалтерия предприятия»;
- файловая база «1С:Торговля и склад»;
- Exchange Mail Server;
- интеграция 1С с ККМ через TCP/IP и OLE.

Текущая модель безопасности в основном опирается на доменную аутентификацию Active Directory и права доступа к папкам. При этом в системах отсутствуют полноценные механизмы классификации данных, централизованного аудита, контроля выгрузок, управления согласиями и контроля жизненного цикла данных.

## 1. Нормативные и архитектурные требования

### 1.1. Требования к защите данных

Для компании критичны следующие требования:

| Требование | Содержание |
|---|---|
| Конфиденциальность | Доступ к данным должен предоставляться только тем пользователям и системам, которым он необходим для выполнения задачи. |
| Целостность | Медицинские записи, результаты анализов, договоры и платежи не должны изменяться без контроля и истории изменений. |
| Доступность | Данные должны быть доступны уполномоченным сотрудникам и пациентам при штатной работе и после сбоев. |
| Минимизация данных | В каждом процессе должны собираться и передаваться только те данные, которые необходимы для конкретной цели. |
| Разграничение доступа | Доступ должен определяться по ролям и атрибутам: врач, ресепшен, кассир, бухгалтер, пациент, лаборатория, аналитик. |
| Аудит | Все операции с медицинскими, персональными и платёжными данными должны логироваться. |
| Управление согласиями | Компания должна фиксировать цели обработки данных и согласия пациента. |
| Удаление и прекращение обработки | Должен существовать процесс блокировки, удаления или прекращения обработки данных по законному запросу субъекта. |
| Безопасность интеграций | Внешние интеграции должны использовать защищённый канал, минимальные API-контракты и проверку прав доступа. |
| Data Lineage | Необходимо понимать, откуда данные появились, куда были переданы и в каких отчётах/моделях использовались. |

### 1.2. Архитектурные практики

| Практика | Как должна применяться |
|---|---|
| Privacy by Design | Защита данных должна проектироваться сразу в архитектуре процессов, API, БД и интерфейсов, а не добавляться после разработки. |
| Data Minimization | Врач, ресепшен, лаборатория, бухгалтерия и аналитика должны получать только минимальный набор данных. |
| Least Privilege | Пользователь получает минимальный доступ, необходимый для работы. |
| Need-to-Know | Даже внутри компании доступ к медицинским данным должен быть ограничен бизнес-необходимостью. |
| RBAC | Базовое разграничение доступа по ролям: врач, ресепшен, кассир, бухгалтер, склад, пациент, администратор. |
| ABAC | Дополнительное разграничение по атрибутам: филиал, лечащий врач, принадлежность записи пациенту, тип данных, статус договора. |
| Audit by Design | Все критичные действия должны автоматически попадать в журнал аудита. |
| Secure API by Default | API по умолчанию не должен возвращать чувствительные поля без явного разрешения. |
| Data Classification | Каждое поле и каждый документ должны иметь категорию чувствительности. |
| Data Lineage | Поток данных должен быть отслеживаемым от источника до потребителя. |

## 2. Аудит текущих мер безопасности

| Область контроля | Текущее состояние As-Is | Оценка | Комментарий |
|---|---|---|---|
| Аутентификация сотрудников | Используется Active Directory / доменная авторизация | Частично достаточно | Есть базовый вход по доменной учётной записи, но не описаны MFA, политика паролей и контроль сессий. |
| Авторизация | Доступ регулируется в основном правами к папкам и файлам | Недостаточно | Нет прикладной модели доступа к конкретным типам данных и медицинским записям. |
| Разделение ролей | Роли фактически определяются должностью, но не закреплены в системах | Недостаточно | Нет формального RBAC/ABAC для врача, ресепшена, кассира, бухгалтера, аналитика и пациента. |
| Хранение медицинских данных | Файлы PDF/JPG/Excel на общем файловом сервере | Критично | Медицинские данные находятся в неструктурированном виде без полноценного аудита и контроля жизненного цикла. |
| Хранение данных пациентов | Excel-файлы и папки пациентов | Критично | Нет единого справочника пациента, контроля дублей, истории изменений и разграничения по полям. |
| Шифрование данных при хранении | Не описано | Недостаточно | Нет подтверждения, что файлы, базы 1С, архивы и резервные копии шифруются. |
| Шифрование при передаче | Не описано | Недостаточно | Не описаны TLS/mTLS для интеграций, передачи файлов и будущего API лаборатории. |
| Аудит действий пользователей | Не реализован или не описан | Критично | Невозможно достоверно определить, кто открыл, изменил, скопировал или удалил файл. |
| Контроль выгрузок | Не описан | Критично | Сотрудник может скопировать Excel/сканы на внешний носитель или отправить по почте. |
| Управление согласиями | Не описано | Критично | Не видно, где фиксируются согласия пациента, цели обработки и сроки хранения. |
| Минимизация данных | Не применяется системно | Критично | Расширенные анкеты собирают больше данных, чем может требоваться для конкретной услуги. |
| Data Lineage | Отсутствует | Критично | Невозможно отследить путь данных от пациента до файлов, 1С, лаборатории, BI и будущих AI/ML-сервисов. |
| Интеграция лаборатории | В целевом состоянии планируется API, сейчас реестры/файлы | Недостаточно | Есть риск передачи избыточных данных лаборатории и получения результатов без строгой привязки к пациенту. |
| Платёжный контур | ККМ интегрирована с 1С, дополнительно ведётся Excel | Недостаточно | Двойной учёт повышает риск ошибок и несанкционированного доступа к финансовым данным. |
| Аналитика | Excel, Jupyter, Python | Критично | Аналитика может строиться на сырых ПДн и медицинских данных без обезличивания. |
| Резервное копирование | Не описано | Требует проверки | Неизвестно, есть ли резервные копии, шифрование бэкапов и тесты восстановления. |
| Мониторинг ИБ | Не описан | Недостаточно | Нет SIEM/централизованного мониторинга событий доступа и аномалий. |
| Физическая безопасность | Сервер находится в том же здании, что офис | Недостаточно | Есть риск физического доступа, отказа питания, пожара, затопления и простоя офиса. |
| Масштабируемость защиты | Один офис, локальный файловый сервер | Недостаточно | При росте филиалов текущая модель доступа и хранения станет неуправляемой. |

## 3. Сопоставление процессов с требованиями безопасности

### 3.1. Регистрация пациента

| Элемент | Текущее состояние | Требуемое состояние | Проблема |
|---|---|---|---|
| Сбор данных | Администратор вручную собирает ФИО, дату рождения, телефон, email, адрес, место работы/учёбы, сведения о заболеваниях | Собирать только данные, необходимые для выбранной услуги | Нарушается принцип минимизации данных |
| Хранение | Excel Patients и папка пациента на файловом сервере | Централизованная CRM/МИС с разграничением доступа | Данные не структурированы и не защищены на уровне полей |
| Согласие | Не описано | Фиксация согласия, цели обработки, версии формы согласия | Нет управления согласиями |
| Аудит | Не описан | Логирование создания, изменения и просмотра карточки пациента | Невозможно расследовать инциденты |
| Доступ | Через папки/файлы | RBAC/ABAC: ресепшен видит только административные данные | Ресепшен может получить доступ к лишним данным |

### 3.2. Запись пациента к врачу

| Элемент | Текущее состояние | Требуемое состояние | Проблема |
|---|---|---|---|
| Запись на приём | Excel-журнал врача | Единая система записи с историей изменений | Нет контроля целостности расписания |
| Данные записи | ФИО пациента, специалист, дата/время | Минимальный набор данных для записи | Возможна передача лишних данных |
| Доступ врача | Врач смотрит свой Excel-журнал и может открывать папку пациента | Врач видит только своих пациентов и медицинские данные по необходимости | Нет ABAC по лечащему врачу и факту приёма |
| Изменение записи | Ручное редактирование Excel | Журналирование изменений | Нет истории изменений |
| Уведомления | Ручные напоминания | Контролируемый сервис уведомлений | Нет контроля, какие данные уходят в уведомления |

### 3.3. Приём пациента и медицинская карта

| Элемент | Текущее состояние | Требуемое состояние | Проблема |
|---|---|---|---|
| Медицинская карта | PDF/JPG/Excel на файловом сервере | Электронная медицинская карта с контролем доступа | Нет целостности и аудита |
| Заключение врача | Файл сохраняется вручную | Структурированная запись с историей версий | Заключение можно изменить без следа |
| Доступ к данным | Через доступ к папке пациента | ABAC: лечащий врач, филиал, назначенный приём, тип документа | Доступ слишком широкий |
| Врачебная тайна | Не выделена как отдельная категория | Тег MEDICAL_SECRET и обязательный аудит | Нет классификации и тегирования |
| Передача пациенту | Вручную, возможно через файл или почту | Через ЛК/мобильное приложение с проверкой принадлежности данных пациенту | Риск отправки не тому получателю |

### 3.4. Анализы и лаборатория

| Элемент | Текущее состояние | Требуемое состояние | Проблема |
|---|---|---|---|
| Назначение анализа | Ручная фиксация | Структурированное назначение в системе | Нет единого идентификатора назначения |
| Передача в лабораторию | Файлы/реестры или будущий API | API через Gateway, TLS/mTLS, минимальный контракт | Риск передачи избыточных данных |
| Идентификация пациента | ФИО и иные данные | Псевдонимизированный идентификатор заказа/пациента | Лаборатория может получить лишние ПДн |
| Получение результата | Excel/file registry | API-ответ с подписью/контролем целостности | Риск подмены или ошибки привязки результата |
| Аудит обмена | Не описан | Логирование всех запросов и ответов | Невозможно расследовать ошибки и утечки |

### 3.5. Оплата медицинских услуг

| Элемент | Текущее состояние | Требуемое состояние | Проблема |
|---|---|---|---|
| Приём оплаты | Кассир, ККМ, 1С | Платёжный шлюз и интеграция с 1С | Текущий процесс плохо масштабируется |
| Дополнительный учёт | Excel + 1С | Один источник правды | Двойной учёт создаёт расхождения |
| Доступ к платежам | Кассиры и бухгалтерия | RBAC: кассир видит платёж, бухгалтер — отчётность | Нет строгого разделения доступа |
| Привязка к пациенту | Может храниться в Excel/1С | Единый идентификатор пациента и платежа | Риск ошибок при сверке |
| Аудит | Не описан | Журналирование операций оплаты, возврата и корректировки | Сложно расследовать спорные операции |

### 3.6. Аналитика, BI, ML и AI

| Элемент | Текущее состояние | Требуемое состояние | Проблема |
|---|---|---|---|
| Источники | Excel, сканы, 1С | Контролируемое озеро данных | Нет управляемого ingestion-процесса |
| Использование ПДн | Возможна работа с сырыми ПДн | Обезличивание/псевдонимизация до аналитики | Высокий риск утечки |
| Data Lineage | Отсутствует | Каталог данных и отслеживание происхождения | Нельзя доказать источник отчёта |
| Доступ аналитика | Доступ к файлам | Доступ к витринам без прямых ПДн | Аналитик может видеть лишние данные |
| ML/AI/LLM | Планируется | Запрет обучения на сырых медицинских данных без отдельного процесса и согласий | Риск попадания ПДн в модели |

## 4. Список проблемных зон

### 4.1. Критичные проблемные зоны

| № | Проблемная зона | Описание риска | Затронутые процессы |
|---|---|---|---|
| 1 | Медицинские данные хранятся в файлах | PDF/JPG/Excel на общем диске не обеспечивают контролируемый доступ, аудит и целостность | Регистрация, приём, анализы |
| 2 | Нет централизованного аудита | Невозможно определить, кто смотрел, изменял, копировал или удалял данные | Все процессы |
| 3 | Нет классификации данных | Система не различает обычные данные, ПДн, медицинскую тайну и платёжные данные | Все процессы |
| 4 | Нет тегирования чувствительных данных | Нельзя автоматически применять политики доступа, шифрования и аудита | Все процессы |
| 5 | Нет принципа минимизации | В процессах могут собираться и передаваться лишние данные | Регистрация, лаборатория, аналитика |
| 6 | Нет Data Lineage | Невозможно отследить путь данных от пациента до отчётов, лаборатории и AI/ML | Аналитика, лаборатория, регистрация |
| 7 | Нет управления согласиями | Не описано, где хранится согласие пациента и как контролируются цели обработки | Регистрация, ЛК, аналитика |
| 8 | Нет механизма прекращения обработки | Не описан процесс удаления, блокировки или исключения данных из обработки | Все процессы |
| 9 | Доступ к данным слишком широкий | Права задаются на уровне папок, а не на уровне конкретных данных и бизнес-контекста | Регистрация, приём |
| 10 | Аналитика использует потенциально сырые данные | BI/ML/AI могут получить реальные ПДн и медицинские сведения | Аналитика |

### 4.2. Значимые проблемные зоны

| № | Проблемная зона | Описание риска | Затронутые процессы |
|---|---|---|---|
| 11 | Двойной учёт оплат в Excel и 1С | Возможны расхождения, ошибки и несанкционированный доступ | Оплата |
| 12 | Файловый режим 1С | Сложно масштабировать, контролировать доступ и обеспечивать отказоустойчивость | Оплата, бухгалтерия, склад |
| 13 | Нет защищённого API-контура | Будущая интеграция лаборатории может раскрыть лишние данные | Лаборатория |
| 14 | Нет проверки ownership для пациента | В будущем пациент может получить доступ к чужим данным при ошибках API | ЛК, мобильное приложение |
| 15 | Нет DLP-контроля | Сотрудники могут копировать или отправлять файлы наружу | Все файловые процессы |
| 16 | Нет мониторинга аномального поведения | Массовое скачивание или доступ вне рабочего времени не будет замечен | Все процессы |
| 17 | Нет политики хранения | Не определено, сколько хранить анкеты, договоры, сканы и аналитические выгрузки | Все процессы |
| 18 | Нет защиты резервных копий | Даже при наличии бэкапов неизвестно, шифруются ли они и кто имеет доступ | Все процессы |
| 19 | Сервер находится в офисе | Физический риск отказа, пожара, кражи или отключения | Вся инфраструктура |
| 20 | Нет разделения контуров | Операционные, медицинские, финансовые и аналитические данные могут смешиваться | Все процессы |
