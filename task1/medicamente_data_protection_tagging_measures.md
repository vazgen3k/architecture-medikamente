# Улучшения защиты данных, тегирование и меры конфиденциальности

## 1. Что можно улучшить

Для перехода от текущего состояния As-Is к безопасной целевой архитектуре необходимо перестать хранить чувствительные данные в Excel, сканах и общих папках как в основном источнике данных. Данные должны быть перенесены в управляемые системы с централизованным доступом, аудитом, тегированием и контролем жизненного цикла.

Основные улучшения:

| Направление | Что улучшить | Ожидаемый результат |
|---|---|---|
| Хранение данных | Перейти от Excel/PDF/JPG на файловом сервере к CRM, МИС/EMR, платёжному контуру и DWH | Данные структурированы, управляемы и защищены |
| Доступ | Внедрить RBAC и ABAC | Пользователь видит только те данные, которые нужны ему по роли и бизнес-контексту |
| Классификация | Ввести категории и теги данных | Система понимает, где ПДн, медицинская тайна, платежи и данные для аналитики |
| Аудит | Логировать все операции с чувствительными данными | Можно расследовать инциденты и выявлять нетипичные действия |
| Интеграции | Использовать API Gateway, TLS/mTLS, минимальные API-контракты | Лаборатория и партнёры получают только разрешённый набор данных |
| Аналитика | Использовать обезличенные и псевдонимизированные данные | BI/ML/AI не работают с сырыми ПДн без необходимости |
| Data Lineage | Внедрить Data Catalog, например Apache Atlas / OpenMetadata | Можно отследить путь данных от пациента до отчёта, API или ML-датасета |
| Логи | Запретить запись ПДн и медицинских данных в application logs | Снижается риск утечки через логи |
| Жизненный цикл | Ввести правила хранения, архивирования, удаления и прекращения обработки | Данные обрабатываются только в рамках целей и сроков |
| Контроль утечек | Внедрить DLP и мониторинг аномалий | Снижается риск массовой выгрузки или отправки данных наружу |

## 2. Список данных для защиты и способы защиты

| Данные | Категория | Теги | Шифрование | Обфускация / маскирование | Обезличивание / псевдонимизация | Комментарий |
|---|---|---|---|---|---|---|
| ФИО пациента | Персональные данные | PII, AUDIT_REQUIRED | Да, at-rest и in-transit | В интерфейсах частичное маскирование при необходимости | Псевдонимизация для аналитики | Нужно врачу, ресепшену и пациенту |
| Дата рождения | Персональные данные | PII | Да | Маскирование в неполных представлениях | Возрастная группа для аналитики | Не всегда нужна точная дата |
| Телефон | Персональные данные | PII, CONTACT | Да | `+7******1234` | Не использовать в BI/ML | Нужен для уведомлений и связи |
| Email | Персональные данные | PII, CONTACT | Да | Частичное маскирование | Не использовать в BI/ML | Нужен для ЛК и уведомлений |
| Адрес регистрации | Персональные данные | PII, SENSITIVE_PII | Да | Скрывать от ролей без необходимости | Регион/город для аналитики | Собирать только при необходимости |
| Место работы/учёбы | Персональные данные | PII | Да | Скрывать в интерфейсах | Категория занятости для аналитики | Следует минимизировать сбор |
| Хронические заболевания | Медицинские данные | MEDICAL_SECRET, SENSITIVE_PII, AUDIT_REQUIRED | Да | Не показывать ролям без доступа | Код/категория без идентификатора пациента | Доступ только врачу и пациенту |
| Диагноз | Медицинские данные | MEDICAL_SECRET, AUDIT_REQUIRED | Да | Не выводить в списках и логах | Обезличенная категория для аналитики | Доступ только врачу и пациенту |
| Назначения врача | Медицинские данные | MEDICAL_SECRET, AUDIT_REQUIRED | Да | Скрывать от ресепшена и кассира | Агрегация для аналитики | Требуется история изменений |
| Медицинское заключение | Медицинские данные | MEDICAL_SECRET, DOCUMENT, AUDIT_REQUIRED | Да | Не логировать содержимое | Псевдонимизация/обезличивание для анализа | Нужен контроль версий и целостности |
| Результаты анализов | Медицинские данные | MEDICAL_SECRET, LAB_RESULT, AUDIT_REQUIRED | Да | Не показывать ролям без доступа | Псевдонимизация для лабораторного обмена | Важно контролировать привязку к пациенту |
| Факт обращения за медпомощью | Врачебная тайна | MEDICAL_SECRET, AUDIT_REQUIRED | Да | Скрывать от неуполномоченных ролей | Агрегированные показатели посещений | Даже факт обращения является чувствительным |
| Запись на приём | Операционные данные + ПДн | PII, APPOINTMENT | Да | Для ресепшена можно ФИО/телефон, без диагноза | Агрегация по слотам и специализациям | Данные нужны для расписания |
| Договор | Договорные данные + ПДн | CONTRACT, PII, AUDIT_REQUIRED | Да | Маскирование реквизитов | Не использовать в ML/AI | Доступ ресепшену, пациенту, бухгалтерии по роли |
| Платёж | Финансовые данные | PAYMENT, AUDIT_REQUIRED | Да | Маскирование чувствительных реквизитов | Агрегация для P&L/ABC | Доступ кассиру и бухгалтерии |
| Данные сотрудника | ПДн сотрудника | EMPLOYEE_DATA, PII | Да | Маскирование зарплатных/кадровых данных | Агрегация для HR-аналитики | Доступ бухгалтерии/HR |
| Зарплата | Конфиденциальные данные сотрудника | EMPLOYEE_DATA, PAYMENT, AUDIT_REQUIRED | Да | Скрывать от всех, кроме бухгалтерии/HR | Агрегация | Высокая чувствительность |
| Логи доступа | Служебные данные безопасности | AUDIT_LOG | Да | Не хранить значения ПДн | Не применимо | Логи должны хранить факт доступа, а не содержимое данных |
| BI-витрины | Аналитические данные | ANONYMIZED, ANALYTICS_ALLOWED | По необходимости | Не должно быть прямых ПДн | Да | Доступны аналитикам после обезличивания |
| ML/AI-датасеты | Производные данные | ML_ALLOWED, ANONYMIZED / PSEUDONYMIZED | Да | Не содержат прямых идентификаторов | Да | Использовать только после проверки тегов |

## 3. Тегирование

### 3.1. Набор тегов

| Тег | Значение | Основные правила |
|---|---|---|
| PUBLIC | Открытые данные | Можно использовать без специальных ограничений |
| INTERNAL | Внутренние данные компании | Доступ только сотрудникам по роли |
| PII | Персональные данные | Шифрование, маскирование, запрет записи в логи |
| SENSITIVE_PII | Чувствительные персональные данные | Усиленный доступ, аудит, минимизация |
| MEDICAL_SECRET | Медицинская тайна | Доступ врачу/пациенту, обязательный аудит, запрет обычного логирования |
| PAYMENT | Платёжные данные | Доступ кассиру/бухгалтерии, аудит операций |
| CONTRACT | Договорные данные | Доступ пациенту, ресепшену и бухгалтерии по роли |
| EMPLOYEE_DATA | Данные сотрудников | Доступ бухгалтерии/HR, шифрование |
| LAB_RESULT | Результаты анализов | Доступ врачу/пациенту, контроль привязки к заказу |
| AUDIT_REQUIRED | Требуется аудит | Все действия записываются в журнал аудита |
| MASK_REQUIRED | Требуется маскирование | Значение скрывается в UI/API/логах |
| ANONYMIZED | Обезличенные данные | Можно использовать для BI и агрегированной аналитики |
| PSEUDONYMIZED | Псевдонимизированные данные | Можно использовать при контролируемом доступе |
| ANALYTICS_ALLOWED | Разрешено для аналитики | Допускается в BI-витринах |
| ML_ALLOWED | Разрешено для ML/AI | Допускается в ML/AI-датасетах после проверки |
| DELETE_ON_REQUEST | Удаление/блокировка по запросу | Данные попадают в процесс прекращения обработки |

### 3.2. Инструмент тегирования

В целевой архитектуре рекомендуется использовать Data Catalog - Apache Atlas.

Apache Atlas должен хранить:

- источники данных: CRM, МИС/EMR, лабораторный контур, платёжный контур, 1С, файловое хранилище, DWH/Data Lake, BI;
- сущности: пациент, запись, медицинская карта, анализ, платёж, договор, сотрудник;
- поля и документы;
- теги чувствительности;
- владельцев данных;
- разрешённые роли;
- правила защиты;
- связи Data Lineage.

## 5. Краткий вывод

Основное улучшение для компании — перейти от файловой модели хранения к управляемой архитектуре данных. В этой архитектуре каждое чувствительное поле или документ имеет тег, владельца, правила доступа и защиты. Доступ к данным должен контролироваться через IAM, RBAC/ABAC и API Gateway, а действия с медицинскими, персональными и платёжными данными должны попадать в аудит. Для аналитики, BI, ML и AI должны использоваться только обезличенные или псевдонимизированные данные, разрешённые для соответствующей цели обработки.
