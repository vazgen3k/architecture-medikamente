# Оценка узких мест при миграции

### [Диаграмма Исикавы](medicamente_ishikawa.drawio.xml)

## Ключевые процессы и компоненты, затрагиваемые миграцией

| Процесс / компонент | Текущее состояние | Целевое состояние | Возможное узкое место |
|---|---|---|---|
| Регистрация пациента | Excel, ручной ввод, папки на файловом сервере | CRM / Patient Service | Ошибки миграции данных, дубли пациентов, неполные карточки |
| Запись к врачу | Excel-журнал врача | Appointment Service | Конкурентные изменения расписания, рост количества запросов |
| Медицинская карта | PDF/JPG/Excel, сканы | Medical Records Service / EMR | Большой объём файлов, сложность структурирования медицинских данных |
| Анализы | Файлы/реестры, ручная обработка | Lab Integration API | Задержки API, ошибки сопоставления результатов с пациентами |
| Оплата | ККМ + 1С + Excel | Billing / Payment Gateway + 1С | Расхождения между платёжным шлюзом, ККМ и 1С |
| Аналитика | Excel, Jupyter, ручные выгрузки | CDC → Kafka → Airflow → DWH/BI | Задержки ETL, некачественные данные, перегрузка DWH |
| Авторизация | AD и права на папки | IAM, RBAC/ABAC, Policy Engine | Неверные роли, избыточные права, задержки проверок доступа |
| Аудит | Не описан | Audit Log + SIEM | Рост объёма логов, сложность корреляции событий |
| Инфраструктура | Один локальный сервер | Распределённая архитектура / Kubernetes / БД / брокер | Нехватка ресурсов, сетевые задержки, SPOF |
| Миграция файлов | Общий диск | Объектное хранилище / структурированные сервисы | Потеря связей между файлами, пациентами и приёмами |

## Выявленные проблемы по категориям

### Инфраструктура

| Возможная проблема | Описание влияния | Риск |
|---|---|---|
| Один локальный сервер в офисе | Отказ сервера или офиса может остановить все ключевые процессы | Высокий |
| Нехватка CPU/RAM/IOPS | Новые сервисы, БД, Kafka, Airflow и аналитика требуют больше ресурсов | Высокий |
| Ограниченная пропускная способность сети | Филиалы, мобильное приложение и лаборатория увеличат сетевой трафик | Высокий |
| Отсутствие отказоустойчивости | Нет описания кластеризации, резервного ЦОДа или автоматического failover | Высокий |
| Недостаточная производительность дисков | Миграция файлов, медицинских документов и логов может перегрузить дисковую подсистему | Средний |
| Отсутствие тестов восстановления | Даже при наличии бэкапов неизвестно, насколько быстро можно восстановить систему | Высокий |

### Программное обеспечение и архитектура

| Возможная проблема | Описание влияния | Риск |
|---|---|---|
| Переход к микросервисам без декомпозиции доменов | Сервисы могут повторить монолитную связанность и стать сложными в сопровождении | Высокий |
| Синхронные цепочки вызовов | Длинные цепочки API-запросов увеличат latency и риск каскадных отказов | Высокий |
| Отсутствие ограничений на API | При росте нагрузки возможны перегрузки backend-сервисов | Средний |
| Недостаточная наблюдаемость | Без метрик, трассировки и логов сложно найти источник деградации | Высокий |
| Некорректная модель данных | Ошибки в доменной модели приведут к дублям, связности и сложной миграции | Высокий |
| Сложность поддержки старых и новых систем параллельно | На переходном этапе возрастает риск рассинхронизации данных | Высокий |

###  Интеграции

| Возможная проблема | Описание влияния | Риск |
|---|---|---|
| Интеграция с 1С в файловом режиме | Файловый режим плохо подходит для высоконагруженного обмена и масштабирования | Высокий |
| Интеграция ККМ через TCP/IP и OLE | Возможны ограничения по стабильности, совместимости и мониторингу | Средний |
| Новое API лаборатории | Задержки или сбои лаборатории могут влиять на выдачу результатов анализов | Высокий |
| Нет единых идентификаторов | Ошибки сопоставления пациента, анализа, платежа и записи | Высокий |
| Отсутствие retry/idempotency | Повторные запросы могут создавать дубли записей, оплат или заказов анализов | Высокий |
| Неописанные API-контракты | Разные команды могут по-разному трактовать состав и формат данных | Средний |

###  Данные и миграция

| Возможная проблема | Описание влияния | Риск |
|---|---|---|
| Данные в Excel и сканах неструктурированы | Автоматическая миграция затруднена, потребуется ручная очистка и нормализация | Высокий |
| Дубли пациентов | Один пациент может быть заведён несколько раз в разных Excel-файлах и папках | Высокий |
| Нет единого идентификатора пациента | Сложно связать записи, договоры, анализы, платежи и медицинские карты | Высокий |
| Некачественные исторические данные | Ошибки ФИО, телефонов, дат рождения и документов ухудшат работу новой системы | Высокий |
| Большой объём PDF/JPG | Перенос файлов может занять много времени и создать нагрузку на сеть/диски | Средний |
| Нет Data Lineage | Невозможно отследить происхождение данных и корректность аналитических витрин | Высокий |
| Сложность обезличивания | Для BI/ML нужно отделить сырые ПДн и медицинские данные от аналитических витрин | Высокий |

###  Безопасность и Privacy

| Возможная проблема | Описание влияния | Риск |
|---|---|---|
| Ошибки RBAC/ABAC | Сотрудник может получить доступ к данным, которые ему не нужны | Высокий |
| Нет проверки ownership для пациента | Пациент может увидеть чужие анализы, договоры или запись | Критический |
| Избыточные данные в API | API может возвращать медицинскую тайну или ПДн там, где это не требуется | Высокий |
| Логи содержат чувствительные данные | Диагнозы, телефоны, ФИО или результаты анализов могут попасть в технические логи | Высокий |
| Нет централизованного управления согласиями | Данные могут использоваться не по той цели обработки | Высокий |
| Нет автоматического контроля тегов | Чувствительные данные могут попасть в BI/ML без обезличивания | Высокий |
| Рост объёма audit logs | Аудит может сам стать узким местом по записи, хранению и анализу событий | Средний |

###  Персонал и процессы

| Возможная проблема | Описание влияния | Риск |
|---|---|---|
| Недостаток опыта эксплуатации микросервисов | У команды есть опыт локальной инфраструктуры, но новая архитектура сложнее | Средний |
| Нет формализованного процесса миграции | Без плана cutover/rollback высок риск простоя | Высокий |
| Сопротивление сотрудников | Ресепшен, врачи и кассиры привыкли к Excel и могут ошибаться в новой системе | Средний |
| Недостаточное тестирование | Ошибки проявятся уже на продуктиве при реальных пациентах | Высокий |
| Нет владельцев данных | Некому принимать решения по качеству, срокам хранения и правилам доступа | Высокий |
| Нет регламентов инцидентов | При сбое или утечке команда может действовать несогласованно | Высокий |

## Рекомендации по устранению узких мест

| № | Рекомендация | Описание | Приоритет |
|---|---|---|---|
| 1 | Провести инвентаризацию и очистку данных до миграции | Выявить источники, дубли, невалидные поля, устаревшие файлы и владельцев данных | Высокий |
| 2 | Ввести единый идентификатор пациента | Связать пациента, записи, договоры, анализы, платежи и медицинские документы | Высокий |
| 3 | Выполнить миграцию поэтапно | Использовать пилотный филиал/процесс, затем расширять покрытие | Высокий |
| 4 | Подготовить план rollback | Для каждого этапа миграции определить способ возврата к предыдущему состоянию | Высокий |
| 5 | Настроить CDC и синхронизацию данных | На переходном этапе обеспечить согласованность старых и новых систем | Высокий |
| 6 | Внедрить API Gateway | Централизовать маршрутизацию, rate limiting, аутентификацию и аудит API | Высокий |
| 7 | Реализовать RBAC/ABAC и ownership checks | Гарантировать, что пациент видит только свои данные, а сотрудники — только нужные данные | Высокий |
| 8 | Настроить Data Catalog и тегирование | Описать PII, MEDICAL_SECRET, PAYMENT, владельцев данных и Data Lineage | Высокий |
| 9 | Обезличивать данные до аналитики | В BI/ML должны попадать только разрешённые обезличенные или псевдонимизированные витрины | Высокий |
| 10 | Провести нагрузочное тестирование | Проверить запись к врачу, ЛК, API лаборатории, платежи, CDC, Kafka, DWH | Высокий |
| 11 | Настроить observability | Метрики, логи, трассировка, алерты, SLO/SLI для ключевых процессов | Высокий |
| 12 | Устранить SPOF инфраструктуры | Настроить резервирование БД, бэкапы, репликацию, отказоустойчивость и восстановление | Высокий |
| 13 | Ограничить синхронные цепочки вызовов | Использовать очереди/шину событий для уведомлений, аналитики и интеграций | Средний |
| 14 | Ввести idempotency и retry | Защитить оплаты, заказы анализов и записи от дублей при повторных запросах | Высокий |
| 15 | Подготовить регламенты для сотрудников | Обучить ресепшен, врачей, кассиров и аналитиков работе в новой системе | Средний |
| 16 | Назначить владельцев данных | Закрепить ответственность за пациентские, медицинские, платёжные и аналитические данные | Средний |
| 17 | Проверить интеграции с 1С и ККМ | Определить ограничения файлового режима, сценарии обмена и мониторинг ошибок | Высокий |
| 18 | Настроить тестовые стенды | Создать dev/test/stage окружения с обезличенными данными | Средний |
| 19 | Настроить контроль логирования | Запретить попадание ПДн и медицинской тайны в application logs | Высокий |
| 20 | Ввести процесс управления инцидентами | Определить ответственных, каналы оповещения, SLA реакции и порядок расследования | Средний |

## Приоритетность мер

### Высокий приоритет


- инвентаризация и очистка данных;
- единый идентификатор пациента;
- поэтапная миграция и rollback-план;
- нагрузочное тестирование;
- API Gateway;
- RBAC/ABAC и ownership checks;
- Data Catalog и тегирование;
- аудит и мониторинг;
- защита интеграций с лабораторией, 1С и ККМ;
- устранение критичных SPOF;
- запрет чувствительных данных в логах.

### Средний приоритет

- оптимизация синхронных цепочек вызовов;
- обучение сотрудников;
- назначение владельцев данных;
- тестовые стенды с обезличенными данными;
- регламенты эксплуатации и инцидентов;
- автоматизация контроля качества данных;
- DLP-контроль выгрузок.

### Низкий приоритет

- расширенная ML/AI-платформа;
- дополнительные витрины данных для аналитики;
- оптимизация затрат на хранение исторических данных;
- расширенный self-service для бизнес-аналитиков.


## Вывод

Миграция компании «Медикаменте» затрагивает критичные бизнес-процессы: регистрацию пациентов, запись к врачу, медицинские карты, лабораторные анализы, платежи и аналитику. Основные узкие места связаны не только с производительностью, но и с качеством данных, интеграциями, безопасностью, организационными процессами и эксплуатационной готовностью команды.

Наиболее рискованные зоны — миграция неструктурированных данных из Excel/PDF/JPG, отсутствие единого идентификатора пациента, интеграции с 1С/ККМ/лабораторией, рост нагрузки на API и БД, а также ошибки в модели доступа к медицинским данным.

Для снижения рисков необходимо использовать поэтапную миграцию, предварительную очистку данных, нагрузочное тестирование, централизованный API Gateway, RBAC/ABAC, Data Catalog, аудит, мониторинг, отказоустойчивую инфраструктуру и план rollback. Такой подход позволит снизить вероятность деградации производительности и обеспечить стабильный переход к целевой архитектуре.
